## 三、五个进阶改造详解

> 这五块是「原本的 CRUD 项目」和「能写进简历的项目」之间的差距所在。

### 改造 1：修复 SQL 注入

**问题**：`ClueMapper.xml` 的手机号模糊查询用了 `${}` 拼接：

```xml
and c.phone like '%${clueQueryDto.phone}%'   <!-- ${} 是字符串直接拼接 -->
```

`${}` 会把参数**原样拼进 SQL**，前端传 `' or '1'='1` 就能绕过条件。而 `#{}` 是**预编译占位符**（等价于 JDBC 的 `?`），参数只当值处理。

**修复**：

```xml
and c.phone like concat('%', #{clueQueryDto.phone}, '%')
```

**面试会被追问**：`${}` 和 `#{}` 的区别？
> `#{}` 走 PreparedStatement 预编译，参数作为值传入，能防注入；`${}` 是文本替换，只适合拼**表名、列名、order by 字段**这类无法预编译的场景，且必须由后端白名单校验，绝不能用在前端传入的值上。

### 改造 2：密码从 MD5 升级为 BCrypt（含平滑迁移）

**问题**：原实现是 `MD5(明文 + "djh")`。MD5 有两个致命问题：
1. **速度太快** —— 显卡每秒能算几十亿次，暴力破解成本极低
2. **固定盐无效** —— 所有用户共用同一个盐 `"djh"`，彩虹表照样能用

**方案**：换成 BCrypt。它的三个特性正好解决问题：
- **自带随机盐**：同一个密码，每个用户存出来的密文都不一样
- **故意算得慢**：可通过 `strength` 参数调节（项目用 10），暴力破解成本指数级上升
- **盐藏在密文里**：不用额外存盐字段，`$2a$10$...` 本身就包含盐

**难点：老数据怎么办？** 直接换算法，所有历史账号都登不上了。所以做了**双算法兼容 + 自动升级**：

```java
public static boolean matches(String rawPassword, String encodedPassword) {
    if (isBcrypt(encodedPassword)) {
        return ENCODER.matches(rawPassword, encodedPassword);   // 新密码：BCrypt 校验
    }
    return legacyMd5(rawPassword).equalsIgnoreCase(encodedPassword);  // 老密码：MD5 校验
}
```

登录成功后**顺手把老密码改写成 BCrypt**，用户无感知：

```java
// UserServiceImpl.login()
upgradeLegacyPassword(user, password);   // 老 MD5 → BCrypt，失败也不影响本次登录
```

**实测结果**（这就是面试可以拿出来的证据）：

```
登录前：558b1aa94403304b0f0ac1eae2884d9f                 ← 32 位 MD5
登录后：$2a$10$qh5P6t1R6Mby3aFzmQy9fOttfns1xT1QGqGwMPgQVvP3B7gS0uyTm  ← BCrypt
再登录：code=1（走 BCrypt 分支，正常）
```

**顺手修掉的两个隐藏 Bug**：`insertUser` 的 SQL **根本没写 password 字段**（而数据库该列是 NOT NULL），`updateUser` 也漏了 password 分支——不修的话，换什么算法都不生效。

### 改造 3：定时任务 + Redisson 分布式锁

**业务问题**：线索分给销售后长期没人跟进，会一直占着归属人，别人也接手不了 → 需要自动回收。

**实现**：`ClueRecycleTask` 每天凌晨 2 点执行，一条 UPDATE 完成回收：

```java
LambdaUpdateWrapper<Clue> updateWrapper = new LambdaUpdateWrapper<>();
updateWrapper.set(Clue::getStatus, 1)      // 回「待分配」
        .set(Clue::getUserId, null)        // 释放归属人
        .set(Clue::getNextTime, null)
        .set(Clue::getUpdateTime, now)
        .eq(Clue::getStatus, 3)            // 只回收「跟进中」
        .and(w -> w.lt(Clue::getNextTime, deadline)
                .or(n -> n.isNull(Clue::getNextTime).lt(Clue::getUpdateTime, deadline)));
```

**为什么必须加分布式锁**：定时任务在**多实例部署**时会同时触发。假设部署了 3 个实例，凌晨 2 点会有 3 个线程同时执行回收 —— 轻则重复处理，重则互相干扰。用 Redisson 的 `RLock` 保证同一时刻只有一个实例真正干活：

```java
RLock lock = redissonClient.getLock("lock:clue:recycle");
boolean locked = lock.tryLock(0, 60, TimeUnit.SECONDS);  // 等待 0 秒，抢不到就跳过
if (!locked) { log.info("未获取到分布式锁（其他实例正在执行），跳过本次"); return; }
try {
    clueService.recycleTimeoutClues(thresholdDays);
} finally {
    if (lock.isHeldByCurrentThread()) { lock.unlock(); }  // 只允许持有者释放，防误删
}
```

**Redisson 比手写 `SET NX` 强在哪**（面试高频）：

| 能力 | 手写 `SET NX` | Redisson |
|------|--------------|----------|
| 原子性 | 可以 | Lua 脚本原子执行 |
| 可重入 | 不支持 | 支持（hash 存重入次数） |
| 自动续期 | 不支持（业务没跑完锁就过期了） | 看门狗自动续期 |
| 安全释放 | 容易误删别人的锁 | 校验 `UUID:线程ID` 后才删 |

**实测验证**：
```
20:02:01  线索自动回收任务执行完成，共同收 1 条超过 7 天未跟进的线索   ← 正常执行
20:02:20  线索自动回收任务执行完成，共同收 0 条                      ← 已无超期数据
（手动往 Redis 写入同名锁 key，模拟其他实例持锁）
20:02:40  线索自动回收任务未获取到分布式锁（其他实例正在执行），跳过本次  ← 锁生效
20:03:00  线索自动回收任务未获取到分布式锁（其他实例正在执行），跳过本次
（删除锁 key）
20:03:20  线索自动回收任务执行完成，共同收 0 条                      ← 恢复执行
```

**工程细节**：`RedissonConfig` 里**刻意不用** `redisson-spring-boot-starter`，因为它会注册自己的 `RedissonConnectionFactory` 覆盖 Spring Boot 原有的 Lettuce 连接工厂，可能影响项目里已有的 Redis 用法。改为手动装配，并加 `@Lazy` 避免 Redis 未启动时应用启动失败。

### 改造 4：缓存三层防护（穿透 / 击穿 / 雪崩）

**背景**：首页概览要跨表聚合统计线索和商机的各状态数量，属于「算得慢、变得少」的典型缓存场景。但直接上缓存会踩三个经典坑，项目逐个做了防护。

#### ① 缓存穿透 —— 空值缓存

**问题**：请求一个数据库里也没有的数据，缓存永远不命中，每次请求都打到数据库。

**解法**：查库结果为空时，**缓存一个空值占位符**，过期时间设短（30 秒）：

```java
if (overview == null) {
    redisTemplate.opsForValue().set(CACHE_KEY, NULL_VALUE_PLACEHOLDER, 30, TimeUnit.SECONDS);
    return null;
}
```

为什么过期时间要短？因为它是「假数据」，万一真实数据后来有了，短过期能让它尽快失效。

> ⚠️ 诚实说明：概览接口是**固定 key + COUNT 聚合**，天然不容易穿透。这段更像通用防御性编程。真正需要防穿透的是 `GET /clues/{id}` 这种**按不存在的 id 反复查库**的接口。面试时如果被追问，这样解释反而显得你理解透彻。

#### ② 缓存击穿 —— 互斥锁重建

**问题**：热点 key 失效的**那一瞬间**，大量并发请求同时发现缓存没了，一起涌向数据库。

**解法**：用 Redis 的 `setIfAbsent`（等价于 `SET NX`）做互斥锁，只让一个线程去查库重建，其他线程短暂自旋等待：

```java
Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(REBUILD_LOCK_KEY, "1", 10, TimeUnit.SECONDS);
if (Boolean.TRUE.equals(locked)) {
    try {
        Object cached = readCache();
        if (cached != null) { return resolve(cached); }  // 双重检查
        return loadFromDbAndCache();
    } finally {
        redisTemplate.delete(REBUILD_LOCK_KEY);
    }
}
// 没抢到锁 → 自旋等待，避免所有线程一起查库
for (int i = 0; i < 5; i++) {
    Thread.sleep(50);
    Object cached = readCache();
    if (cached != null) { return resolve(cached); }
}
```

**关键设计**：**双重检查**（Double Check）。抢到锁之后要再读一次缓存 —— 因为在你抢锁的过程中，前一个持锁线程可能已经把缓存建好并释放锁了，这时直接返回即可，不必再查一次库。

**实测验证**：清空缓存后同时发 10 个并发请求，日志显示：
```
缓存未命中，查询数据库并重建缓存        ← 只有 1 次！
等待其他线程重建缓存后命中  × 9         ← 其余 9 个都等锁后直接命中
```

#### ③ 缓存雪崩 —— 随机过期时间

**问题**：大批缓存**同一时刻集体失效**，DB 瞬时压力飙升。（典型场景：系统上线时批量预热，都设了 30 分钟过期，那么 30 分钟后全部失效）

**解法**：过期时间 = 基础时间 + 随机值，把失效时刻打散：

```java
long expireSeconds = TimeUnit.MINUTES.toSeconds(5)
        + ThreadLocalRandom.current().nextInt(60);   // 300 + 随机 0~59 秒
redisTemplate.opsForValue().set(CACHE_KEY, overview, expireSeconds, TimeUnit.SECONDS);
```

**实测验证**：`redis-cli` 查看缓存 TTL = **347 秒**（即 300 + 随机 47），证明随机生效。

### 改造 5：操作日志异步化 + 批量落库

**改造前**：`LogAspect` 切面里**同步**写库 —— 每次带 `@LogOperation` 的请求，用户都要等日志写完；而且**一条日志一次 insert**，就是一次数据库往返。

**改造后**：

```
业务方法执行完
   ↓
生产者：日志转 JSON → LPUSH 到 Redis 队列 QUEUE:OPERATE_LOG   ← 主流程立即返回
   ↓
消费者：定时任务每 5 秒 RPOP 一批（最多 100 条）
   ↓
       反序列化 → 一条 insert 批量落库
```

**三个收益**（面试可讲）：

1. **异步解耦** —— 主流程不用等日志落库，响应更快
2. **削峰填谷** —— 突发流量下日志先堆队列，消费者按自己节奏消化
3. **批量写优化** —— 一条 `insert ... values (...),(...)` 代替 N 次 `insert`

**批量插入的 SQL 长这样**（`OperateLogMapper.xml` 用 `<foreach>` 拼出多组 values）：

```xml
<insert id="insertBatch">
    insert into operate_log (operate_user_id, operate_time, class_name, ...)
    values
    <foreach collection="list" item="item" separator=",">
        (#{item.operateUserId}, #{item.operateTime}, #{item.className}, ...)
    </foreach>
</insert>
```

**实测验证**：
```
触发 2 次 @LogOperation 调用后：
  队列长度 = 2，数据库日志条数 = 0      ← 异步生效，业务没等日志
等 5 秒（消费者跑一轮）后：
  队列长度 = 0，数据库日志条数 = 2      ← 批量落库完成

服务端 SQL 日志：
  insert into operate_log (...) values (?,?,?,?,?,?,?) , (?,?,?,?,?,?,?)   ← 一条 SQL 插 2 条
  操作日志异步落库完成，本批 2 条
```

**降级设计**：Redis 不可用时，生产者 `catch` 住异常并**回退为同步落库**，保证「日志不丢 + 业务不受影响」。这也是为什么改造后原有功能完全正常。

**为什么用 Redis 队列而不是 RabbitMQ？**
> 本项目环境没有部署 MQ 中间件。如果硬引 RabbitMQ，broker 不可用时日志切面每次调用都会失败，反而破坏原有功能。Redis List（`LPUSH` + `RPOP`）能实现同样的异步/解耦/削峰语义，且零新增基础设施。将来要换成 RabbitMQ，只需替换生产者的投递方法和消费者的拉取方法，**业务代码零改动**。
>
> 诚实补充：Redis List 做队列**没有 ACK 机制**，消息出队后如果落库失败会丢。要做得更严谨，可以用 `RPOPLPUSH` 把消息转入「处理中队列」，处理成功再删除，处理失败就留在备份队列里补偿。

## 四、面试高频追问与答法

| 追问 | 怎么答 |
|------|--------|
| 你这个 Starter 是怎么被 Spring Boot 加载的？ | Spring Boot 3 通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 这个 SPI 文件读取自动配置类全限定名，然后根据 `@Conditional` 系列条件决定是否生效。我在文件里注册了 `AliyunOSSAutoConfiguration`。 |
| 为什么要用 ThreadLocal 存当前用户？不用会怎样？ | 避免 Service 层每个方法都传 userId 参数，调用链解耦。**但必须在请求结束后 `remove()`** —— Tomcat 线程池会复用线程，不清理会导致上一个请求的用户信息泄漏给下一个请求，同时造成内存泄漏。我在 `afterCompletion` 里做了清理。 |
| 你的定时任务重复执行怎么办？ | 用 Redisson 分布式锁。多实例同时触发时，只有抢到锁的实例执行，其他实例直接跳过。锁设置了租期防止死锁，释放前校验 `isHeldByCurrentThread()` 防止误删别人的锁。 |
| 缓存击穿和缓存穿透的区别？ | 穿透是查**数据根本不存在**（DB 也没有），击穿是**热点 key 失效瞬间**大量并发打 DB。穿透靠缓存空值解决，击穿靠互斥锁/逻辑过期解决。 |
| 你把日志改成异步，用户看不到日志了怎么办？ | 日志不是强一致需求，允许最终一致。消费者 5 秒一轮，最多延迟 5 秒。如果业务要求实时，可以缩短消费间隔或改回同步。 |
| 你的 Redis key 为什么是乱码？ | 因为 `RedisTemplate<Object,Object>` 默认用 JDK 序列化，key 被序列化成二进制。功能没问题，但排查不方便。正确做法是配置 `StringRedisSerializer`（我在消息队列里已经改用 JSON + StringRedisTemplate 了）。 |
| 项目里为什么有两套分页？ | 历史遗留 —— 早期用 PageHelper，后期引入 MyBatis-Plus 自带分页插件。两套同时生效会让 SQL 出现**两个 LIMIT** 而报错。正确做法是统一用 MyBatis-Plus 分页。 |

## 五、项目已知短板（别被问穿）

诚实承认短板，比被面试官问出来要好得多：

| 短板 | 建议的答法 |
|------|-----------|
| 单体应用，没有微服务拆分 | "这是我第一个完整的单体项目，微服务拆分我在下一阶段学习中" |
| 只有概览接口用了缓存 | 已补三层防护，但缓存场景确实偏少 |
| Redis 队列没有 ACK | 日志场景可接受；要严谨需要 `RPOPLPUSH` 补偿或换 RabbitMQ |
| 数据库没有分库分表、读写分离 | 项目数据量小，暂不需要 |
| 缺少单元测试 | 计划补 Service 层单测 + MockMvc 接口测试 |
| 无接口文档 | 计划引入 Knife4j |
| 没有 Docker 部署 | 环境未装 Docker，部署用的是 Nginx + jar |
